# Devlog - 2026-09-10 (part 3)

## Scaling: Diagnosis, Load Testing, Autoscaling

A 2GB VM struggling to run this server turned out to be a build problem,
not a runtime one — `cargo build --release` pulling in `rusqlite`
(bundled), full `tokio`, and `reqwest`+`rustls` across 97k lines of
workspace source is a classic small-VM OOM, and this repo already has the
fix wired up: `.github/workflows/docker-publish.yml` builds and publishes
`ghcr.io/<owner>/openmmo-server` on every push, and `docker-compose.yml`
already defaults to pulling it. The small VM never needs to compile
anything.

Measured (not guessed) the static data footprint while here:
`data-src/*.csv` totals ~50KB on disk — item, monster, NPC, merchant,
dungeon defs. Nowhere near enough to explain a memory problem; terrain is
on-demand procedural generation with a tile cache that starts near-empty.

New tooling, both under `tools/`:

- **`tools/loadtest`** — a new workspace member: a minimal, LLM-free bot
  that logs in via the existing `AuthenticateNpc` path and just holds the
  connection open, for measuring real memory-per-player instead of
  estimating from struct sizes. `measure.sh` ramps it against a running
  container while sampling `docker stats`, writing a CSV. Respects
  `conn_limit.rs`'s per-IP rate limit by design (documented, not worked
  around).
- **`tools/autoscale/watch-and-resize.sh`** — samples memory % and
  established-connection count on a timer; past a threshold, resizes the
  VM up a tier via the cloud provider's API (Hetzner shown as the worked
  example). `DRY_RUN=true` by default — this reboots a real server and
  costs real money, so it doesn't act unattended until told to.

Also wrote up why this server can't horizontally autoscale the way a
stateless API would (single authoritative process holding the whole
world), and sketched the pragmatic alternative — independent world
instances/channels, not fine-grained zone sharding — as a design note for
later, not something built today.

Full writeup: `doc/SCALING.md`. Note for whoever pushes this: `Cargo.lock`
needs a `cargo build`/`cargo update` pass (unlocked) to pick up the new
`tools/loadtest` workspace member before `ci.yml`'s `--locked` build runs.
