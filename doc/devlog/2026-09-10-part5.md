# Devlog - 2026-09-10 (part 5)

## Playtest Triage: Terrain Coverage, Combat Audio, and Four Honest Non-Fixes

Six issues came back from a real deployment (NCP standard, 2vCPU/8GB).
Investigated all six; fixed what could be verified, documented the rest
clearly rather than guessing.

**Found the real cause of the map/movement complaints.** Cross-referencing
`doc/TERRAIN_GENERATION.md` (full world = region range `-16..15`, 32×32
regions, 262,144 tiles) against `docker-compose.yml`'s actual default
(`TERRAIN_REGION_MIN=-2`, `TERRAIN_REGION_MAX=1` — a 4×4-region patch, ~1.5%
of the documented world by area) turned up a real mismatch: the compose
default was always a small dev/demo patch, not the full world, and nothing
said so at bake time. Shipped as-is, movement works fine inside that patch
and looks broken at its edge. Added a loud warning to `terrain-bake.sh` when
the region range is near that default. Didn't change the default itself or
rebake — that's a disk-space (computed a ~6.5GB floor from documented
per-tile sizes, height+splat only; vegetation data adds more by a
content-dependent amount — corrected an earlier, uncomputed "66GB" guess
once the arithmetic was actually done) and deploy-time decision, not
something to silently change underneath a running deployment.

**Auto-hunt already exists.** Almost built a duplicate before actually
reading `combat.ts`'s `combatController` — target a monster and it already
auto-chases and auto-repeats attacks (`attack_cycle`) until the target dies,
with 27 passing unit tests covering the logic in isolation. The reported
"doesn't work" is far more likely a symptom of the terrain patch issue
(pathing into unbaked terrain) than a missing feature. No new code — writing
a second auto-hunt system on top of a working one would just make it harder
to tell which path actually runs.

**Fixed: party members' combat sounds.** `monsterManager.ts` had a real,
specific bug — hit/miss sounds were gated to `isLocalPlayerAttack` only, so
other players' swings played nothing. Removed the gate, added distance-based
volume falloff (full at 8m, silent past 30m). Other players' weapon material
isn't visible client-side (`Player` broadcasts don't carry equipment,
unlike `Character.equipment` server-side), so non-local attacks fall back to
the default material sound — exact per-weapon sound for everyone is a
protocol change, left for later. Verified for real this time: `svelte-check`
before/after identical (13 pre-existing, unrelated errors), full suite 464/467
passing (3 pre-existing failures, unrelated: missing WASM build, missing GLB
asset).

**Fixed (logic-verified, not eyeballed): entity overlap.** No
separation/collision-avoidance existed between players, monsters, and NPCs
at all — confirmed, nothing was there. Added
`client/src/lib/utils/entitySeparation.ts`'s `separateOnGroundPlane`, a
pure function that nudges a monster's *rendered* position away from the
player when closer than a flat 0.7m, leaving the real server-authoritative
position (and everything that reads it — range checks, hit detection)
untouched. Wired into `GameSceneMonstersLayer.svelte`'s `displayPosition`,
preserving its existing object-identity-reuse optimization. 8 new unit
tests cover the math (no-op when far, exact boundary, correct push
distance and direction, Y untouched, no input mutation, same-position
degenerate case) — all pass, full suite now 472/475 (same 3 pre-existing
unrelated failures). Flagged clearly in the doc: this verifies the *math*,
not whether 0.7m actually looks right on screen — that needs a human
looking at it.

**Left undone, on purpose:** building placement (apply_houses.rs — no
obvious bug found, likely same terrain-patch root cause, not worth guessing
at); lag (can't profile a deployment I can't run).
