# 리팩토링 문서: 2026-09 플레이테스트 이슈

NCP 스탠다드(2vCPU/8GB)에 실제로 배포해서 플레이해본 뒤 나온 신고
6건을 정리한다. 각 항목에 **확인된 사실**, **원인 판단(확신도 표시)**,
**이번에 실제로 고친 것 / 고치지 않고 다음 단계로 남긴 것**을 구분해서
적는다. "다 고쳤다"고 말하고 싶지 않아서, 이 구분을 제일 중요하게
지켰다.

## 요약 표

| 신고 | 상태 | 확신도 |
| ---- | ---- | ------ |
| 자동사냥 안 됨 | 🔍 원인 재진단 — 기능은 이미 있음, 범인은 아래 터레인 문제로 추정 | 중 |
| 맵이 제대로 생성 안 됨 | ✅ **근본 원인 확정 + 실제로 고침** (전체 월드 기본값 + 자동 재베이크 + 디스크 안전장치) | 높음 (문서 교차검증 + 실제 스크립트 테스트) |

| 버벅임 | ❓ 재현 불가 — 가설만 | 낮음 |

| 파티원 행동 소리 안 들림 | ✅ **구현 완료, 테스트 통과** | 높음 |

## 1. 맵이 제대로 생성되지 않음 — 근본 원인을 찾았다

**확신도: 높음.** 두 문서를 교차 대조해서 나온, 추측이 아닌 결론이다.

- `doc/TERRAIN_GENERATION.md` 5.1절: 전체 월드는 **32km × 32km = region
  범위 `-16..15` (32×32 regions, 262,144타일)**로 명시돼 있다.
- 그런데 `docker-compose.yml`의 실제 기본값은
  `TERRAIN_REGION_MIN=-2`, `TERRAIN_REGION_MAX=1` — **4×4 = 16
  regions**다. 전체 월드 면적의 **약 1.5%**밖에 안 된다.

이게 왜 문제냐면, `docker/terrain-bake.sh`의 기존 주석이 이미 알려주고
있었다: "erosion과 road generation은 region 범위와 무관하게 항상 전체
32×32km 월드를 시뮬레이션한 뒤 타일을 쓴다" — 즉 **전역 시뮬레이션은
항상 전체 월드 기준으로 돌지만, 실제로 디스크에 써지는 타일 파일은
설정된 region 범위 안에서만** 생긴다. 기본값 그대로 배포하면 스폰
지점 주변 작은 패치만 타일이 존재하고, 그 바깥은 **베이크된 적 없는
땅**이다.

플레이어 입장에서 이게 어떻게 보이냐면 — 정확히 신고하신 증상들과
일치한다:
- 작은 패치 안에서는 멀쩡히 움직이다가 그 경계에서 "이동이 자유롭지
  못함"
- 경계 바깥은 지형 데이터가 없으니 "맵이 제대로 생성이 안 됨"
- 자동사냥(아래 2번)의 추적 경로가 그 경계를 넘어가면 길찾기가 꼬임

왜 기본값이 이렇게 작냐면 — 전체 월드를 다 구우면 디스크가 꽤
필요하다. 정확한 "65MB/region" 같은 수치가 문서 어디에도 없길래
`doc/MAP_DESIGN.md`에 명시된 타일당 크기(하이트맵 8,450바이트 +
스플랫맵 16,384바이트 = 24,834바이트/타일)로 직접 계산해봤다 —
262,144타일 전체면 **최소 약 6.5GB**(하이트맵+스플랫맵만). 여기에
나무·풀 바이너리(Phase 8, `trees/`·`grass/`)가 더 붙는데 이건
지형 내용에 따라 타일마다 크기가 달라서 정확한 총량은 실측 전엔 모른다
— 그러니 6.5GB를 "바닥값"으로 보고, 실제로는 그보다 더 든다고
가정하는 게 안전하다. 처음에 제가 "약 66GB"라고 적었던 건 제대로
검산 안 한 수치였다 — 바로잡는다. 정확한 값은 넓혀서 구워보고
`du -sh data/terrain`으로 직접 재는 게 제일 확실하다.

어느 쪽이든 — 로컬 개발에서 `docker compose up` 한 번에 몇 GB를 바로
요구하면 무거우니, 작은 기본값이 "빠른 시작"용으로 들어가 있던 것으로
보인다. 다만 이게 **운영 배포에도 그대로 흘러간다는 걸 경고하는 장치가
어디에도 없었다.**

### 이번에 실제로 고친 것 (디스크 50GB 확보 후 추가 작업)

처음엔 경고 로그만 추가하고 멈췄는데, 디스크가 50GB라길래 실제로 세
가지를 더 고쳤다.

1. **`docker-compose.yml` 기본값을 전체 월드로 바꿨다**
   (`TERRAIN_REGION_MIN=-16`, `TERRAIN_REGION_MAX=15`). 디스크가
   부족한 배포를 위해 env var로 여전히 덮어쓸 수 있다.
2. **`terrain-bake.sh`가 region 범위 변경을 스스로 감지하게 했다.**
   기존엔 `worldgen.json`이 있으면 무조건 "이미 구웠다"고 건너뛰어서,
   `TERRAIN_REGION_MIN/MAX`만 바꾸고 재시작해도 **아무 일도 안
   일어나는 버그**가 있었다(지난 턴에 발견). `worldgen.json`엔 이미
   `baked_region_range`가 기록돼 있길래(새 필드를 만들 필요가 없었다),
   그 값과 지금 설정된 범위를 비교해서 다르면 자동으로 다시 굽는다 —
   이제 `TERRAIN_FORCE_BAKE`를 수동으로 안 켜도 된다.
3. **베이크 전 디스크 여유 공간을 미리 확인한다.** 타일당 실측
   크기(24,834바이트) × region 수 × 3배(나무/풀 데이터 안전마진) +
   1GB 패딩으로 필요량을 추정하고, 여유 공간이 부족하면 — 3분 넘게
   걸리는 베이크를 시작하지도 않고 — **바로 에러로 거부한다.**
   `TERRAIN_SKIP_DISK_CHECK=1`로 이 체크를 건너뛸 수도 있다.

### 검증

이번엔 `sh -n`/shellcheck만이 아니라, **가짜 `terrain-gen`·`chown`
바이너리를 만들어서 스크립트를 실제로 실행**해봤다:
- worldgen.json 없음 → 베이크 ✅
- 기존 범위와 설정이 일치 → 스킵 ✅ (exit 0)
- 설정이 바뀜(작은 패치 → 전체 월드) → 자동 재베이크 시도, 이 테스트
  환경의 실제 여유 공간(9GB)보다 추정 필요량(약 20GB)이 커서 **베이크
  시작 전에 정확히 거부됨** ✅ (기존 worldgen.json은 안 건드리고 보존)
- 더 작은 범위(디스크에 맞는)로 바꿈 → 자동 재베이크 성공 ✅
- `TERRAIN_SKIP_DISK_CHECK=1` → 추정치 무시하고 진행 ✅
- `TERRAIN_FORCE_BAKE=1` → 범위가 같아도 강제로 다시 구움 ✅

6가지 분기 전부 의도대로 동작하는 걸 실제 실행으로 확인했다 — 이번
세션에서 가장 꼼꼼하게 검증한 코드다.

### 남은 할 일 (사용자가 해야 하는 것)

이 리포를 재배포(`docker compose up -d` 또는 CI 재빌드 후 pull)하면
기존 `worldgen.json`(작은 패치)과 새 기본값(전체 월드)이 자동으로
안 맞는 걸로 잡혀서 **알아서 다시 굽는다** — 수동으로 뭘 더 설정할
필요는 없다. 다만:
- 베이크가 몇 분 이상 걸릴 수 있다(region 수가 16배로 늘었다 —
  "전역 시뮬레이션은 ~3분 고정, 타일 쓰기는 region 수에 비례"이므로
  순수 쓰기 시간은 늘어난다).
- 혹시 디스크 추정치가 틀려서 거부되면, 로그에 찍히는 실제 여유
  공간/추정 필요량을 보고 `TERRAIN_REGION_MIN/MAX`를 조정하거나
  `TERRAIN_SKIP_DISK_CHECK=1`로 직접 판단해서 진행하면 된다.

## 2. 자동사냥이 안 됨 — 사실은 이미 있는 기능이다

**확신도: 중간 (기능 존재는 확인, 실패 원인은 추정).**

처음엔 "자동사냥 기능이 없다"고 가정하고 새로 만들려 했는데, 코드를
보니 **이미 있었다.** `client/src/lib/components/player-control/fsm/combat.ts`의
`combatController` — 몬스터를 타겟으로 지정하면:
1. 범위 밖이면 자동으로 추적 이동(`chasing`)
2. 사거리에 들어오면 자동으로 공격 시작(`reached_attack_range` →
   `beginAttack`)
3. 그 뒤로는 **재클릭 없이 `attack_cycle`이 반복 발사**되어 대상이
   죽을 때까지 계속 공격한다

이 로직을 커버하는 기존 단위 테스트(`combat.test.ts` 23개,
`combatController.test.ts` 4개) 전부 통과한다 — 로직 자체는 격리된
상태에서 정상이다. 그래서 "기능이 고장났다"가 아니라 "기능이 작동할
조건이 안 됐다"일 가능성이 높다고 본다.

가장 유력한 후보가 **위 1번 터레인 문제다**: 추적 이동은 서버·클라이언트
양쪽에서 길찾기/지나갈 수 있는지(passability) 데이터에 의존하는데,
베이크 안 된 지형 위에서는 이 데이터 자체가 없거나 이상할 수 있다.
타겟이 베이크된 패치 경계 밖에 있거나, 추적 경로가 그 경계를 지나가면
"추적이 멈추거나 사거리에 영원히 못 들어가는" 식으로 보일 수 있다 —
플레이어 입장에선 "자동사냥이 안 된다"와 구분이 안 가는 증상이다.

### 이번에 한 것

새 자동사냥 기능을 만들지 않았다 — 이미 있는 걸 또 만들면 중복
로직이 생기고, 어느 쪽이 실제로 동작하는지도 헷갈리게 된다. 대신
이 문서에 "이미 있다"는 사실과 유력 원인을 남긴다.

### 확인해볼 것 (다음 단계)

1번의 region 범위를 넓혀서 재배포한 뒤에도 같은 증상이면, 그때는
`combatController`가 실제로 어떤 입력에서 멈추는지(타겟 지정 자체가
안 되는지, 추적까지는 되는데 공격 전환이 안 되는지) 재현 로그를 보고
다시 봐야 한다 — 지금은 그 구분이 안 돼서 코드를 더 손대지 않았다.

## 3. 마을 건물이 재생성해도 제대로 안 보임

**확신도: 중간.** `tools/terrain-gen/src/apply_houses.rs`를 읽어봤는데
명백한 버그(예: 자원 부족 시 조용히 건너뛰는 코드)는 못 찾았다 —
`skip_flatten`/`skip_grass`/`skip_trees`는 명시적 옵션이지 자동
폴백이 아니고, 에러 삼키기 패턴도 안 보였다.

가장 가능성 높은 설명은 역시 1번과 같다 — 재생성을 여러 번 하신 것
자체가, 작은 기본 region 범위 안에서 마을이 걸쳐 있거나 경계 근처에
있어서 매번 결과가 다르게 보였을 가능성이다. apply_houses.rs 자체의
개별 버그라고 확신할 근거는 못 찾았다.

### 이번에 한 것

코드 레벨에서 명백한 결함은 못 찾았다. 1번(전체 월드 재베이크)이
이번에 실제로 적용됐으니, 마을이 예전 작은 패치의 경계 근처에 있어서
매번 다르게 보였다는 가설이 맞다면 **재배포 한 번으로 같이 해결될
가능성이 높다.** 재배포 후에도 같은 증상이면, 그때는 `apply_houses.rs`
버그일 가능성이 커지는 거라 다시 봐야 한다 — 확신 없는 코드를
"고쳤다"고 내놓지 않는 원칙은 그대로 유지한다.

## 4. 버벅임(lag)

**확신도: 낮음.** 이건 솔직히 이 세션에서 재현할 방법이 없다 — 저는
실제 클라이언트를 렌더링해서 눈으로 보거나 프레임을 측정할 수 없고,
NCP 서버의 실제 부하 상황도 알 수 없다.

구조적으로 짚을 수 있는 것만 적는다:
- 1번 문제(베이크 안 된 지형 경계)에서는 경로탐색이 반복적으로
  실패/재시도할 수 있어 CPU를 불필요하게 먹을 가능성이 있다.
- `tools/loadtest`(지난 세션에서 만든 부하 테스트 도구)로 동접 환경을
  재현하면서 서버 메모리/CPU를 실측하는 게, 추측보다 정확한 다음
  단계다.

### 다음 단계

1번을 고친 뒤에도 버벅이면, 그게 서버 쪽(틱 처리 지연)인지 클라이언트
쪽(렌더링)인지부터 구분해야 한다 — 서버는 `docker stats`로, 클라이언트는
브라우저 개발자도구 성능 탭으로 직접 재는 게 가장 빠르다.

## 5. 몹/NPC와 부딪혀도 그림이 겹쳐서 부자연스러움

**확신도: 원인 파악 높음, 로직 구현도 테스트로 검증 — 다만 "실제로 보기
좋은가"는 이번에도 확인 못 했다.** 코드를 찾아봤는데
**플레이어·몬스터·NPC 사이에 서로 겹치지 않게 밀어내는 로직 자체가
없었다.** `client/src/lib/managers/dungeonManager.ts`에만 `PLAYER_RADIUS
= 0.3`을 쓰는 벽 충돌 처리가 있을 뿐, 엔티티끼리의 분리(separation)
동작은 어디에도 없었다.

### 구현한 것

서버 권위는 전혀 건드리지 않는 **순수 시각적 보정**을 만들었다 — 실제
좌표(서버가 아는 "진짜" 위치, 거리/명중 판정이 쓰는 값)는 그대로
두고, 화면에 그릴 위치만 플레이어와 가까운 몬스터를 살짝 밀어낸다.

- `client/src/lib/utils/entitySeparation.ts`의
  `separateOnGroundPlane(viewer, target, minDistance)` — viewer-target
  거리가 `minDistance`보다 가까우면 정확히 `minDistance`만큼 같은
  방향으로 밀어낸 좌표를 반환, 아니면 `null`(겹치지 않는 절대다수의
  몬스터는 기존 객체를 그대로 재사용 — 매 프레임 불필요한 Three.js
  업데이트를 피하던 기존 월드랩 최적화 패턴을 그대로 따름).
- `GameSceneMonstersLayer.svelte`의 `displayPosition`에 연결. 반지름은
  일단 `0.7`(미터) 고정값이다 — 몬스터 종류별 실제 크기 데이터를
  구하지 못한 채로(화면을 못 보는 상태에서) 작업해서, 종류별 튜닝은
  다음 단계로 남긴다.

### 검증한 것 / 못 한 것

이번엔 "로직이 맞는가"는 순수함수라 단위 테스트로 제대로 검증했다 —
`entitySeparation.test.ts` 8개: 안 겹칠 때 null, 경계값, 정확히
minDistance로 밀려나는지, 방향 보존, Y 미변경, 입력 객체 불변,
동일좌표 축퇴 케이스, 매번 새 객체 반환. 전부 통과하고 `svelte-check`도
수정 전후 동일(13건, 전부 기존 WASM 미빌드 이슈)하다.

다만 이건 "수학이 맞다"를 보장할 뿐 **"실제로 화면에서 자연스럽게
보이는가"는 여전히 사람이 직접 봐야 아는 영역**이다 — 반지름 0.7m가
너무 작아서 여전히 겹쳐 보이거나, 너무 커서 몬스터가 눈에 띄게
"미끄러지는" 것처럼 보일 수 있다. 실제로 플레이해보고 숫자를
조정하는 게 다음 단계다.

## 6. 파티원의 전투 행동 소리가 들리지 않음

**확신도: 높음. 구현 완료, 테스트로 검증했다.**

`client/src/lib/managers/monsterManager.ts`에서 정확한 원인을
찾았다 — 전투 효과음(`playSwordHitSound`/`playSwordMissSound`)이
`isLocalPlayerAttack`일 때만 재생되도록 **의도적으로 막혀 있었다.**
"사운드 기능이 아예 없다"가 아니라 "내 공격 소리만 들리게 막아놓은
기존 설계"였다.

### 고친 것

- 다른 플레이어의 공격도 소리가 나도록 그 조건을 없앴다.
- 다만 다른 플레이어가 어떤 무기를 쥐고 있는지는 지금 클라이언트에
  전혀 보이지 않는 정보라(서버가 `Player` 브로드캐스트에 장비 정보를
  안 담음 — `Character.equipment`는 서버 쪽에만 있음), 본인 공격은
  무기 재질별 정확한 소리, 남의 공격은 기본 소리로 재생된다. 완전히
  정확하게 하려면 서버가 장비 정보를 브로드캐스트해야 하는데, 이건
  프로토콜 변경이라 범위를 넘어서 다음 단계로 남긴다.
- 거리에 따라 소리가 작아지도록 감쇠도 추가했다(8m 이내 풀볼륨,
  30m부터 무음) — 파티원이 옆에서 싸우면 또렷하게, 멀리서 싸우면
  은은하게 들리게.

### 검증

- `npm run` 기반 `svelte-check` — 수정 전후 에러/경고 개수 동일(13건,
  전부 WASM 빌드 안 한 환경 탓의 기존 이슈, 제가 만든 파일 포함
  아님).
- 전체 단위 테스트 464개 통과, 실패 3건은 전부 이 수정과 무관한
  기존 환경 이슈(WASM 미빌드, 누락된 GLB 에셋 파일).
- `sfxManager.test.ts` 5개 개별 재확인 통과.

구현: `client/src/lib/managers/sfxManager.ts`,
`client/src/lib/managers/monsterManager.ts`.

## 검증 환경에 대한 솔직한 한계

이 세션은 Rust 서버 쪽은 `rustc`/`cargo` 1.75(샌드박스의 apt 버전)로
**문법 검증까지만** 가능했다 — 실제로 이 프로젝트를 컴파일하려면
`std::sync::LazyLock`(1.80+) 등을 요구해서, 로컬 빌드로 진짜 메모리를
측정하려던 시도(1번 문제의 실측)는 끝내 실패했다. 대신 **문서
교차검증**으로 원인을 좁혔다 — 추측이 아니라 `doc/TERRAIN_GENERATION.md`와
`docker-compose.yml`을 직접 대조한 결과다.

클라이언트(TypeScript/Svelte) 쪽은 Node/npm이 실제로 동작해서
`svelte-check`와 `vitest`로 **진짜 타입체크·테스트 통과**까지
확인했다 — 6번(사운드)과 5번(겹침 보정)이 신뢰도 높게 검증된 이유다.
다만 5번은 로직만 검증했다는 한계가 있다 — 순수 함수의 입출력이 맞는
것과 화면에서 자연스러워 보이는 것은 다른 문제이고, 후자는 사람이
직접 렌더링을 봐야 확인할 수 있다.

`docker/terrain-bake.sh`(1번)는 셸 스크립트라 다른 검증 방법을
썼다 — 가짜 `terrain-gen`/`chown` 바이너리를 만들어 PATH에 올리고
스크립트를 실제로 실행해서, 분기 6개(최초 베이크/일치 시 스킵/불일치
시 재베이크/디스크 부족 시 거부/스킵 플래그/강제 플래그) 전부 의도한
exit code와 출력을 내는지 직접 확인했다. 문법 검사보다 훨씬 강한
검증이고, 이번 세션에서 가장 꼼꼼하게 테스트된 코드다.
